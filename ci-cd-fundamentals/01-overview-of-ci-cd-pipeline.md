# End-to-End CI/CD Pipeline Overview

This SOP is divided into two main sections:

1. **CI Process** (what happens step-by-step)
2. **CD Process** (what happens after CI)

---

## Architecture Scope

This SOP describes the end-to-end CI/CD workflow using:

- Jenkins Master and Jenkins Agent for Continuous Integration (CI)
- SonarQube for static code analysis
- Trivy for container image vulnerability scanning
- Docker Hub (or another container registry) for storing container images
- Argo CD for Continuous Deployment (CD)
- Kubernetes as the runtime platform

This SOP documents two GitOps deployment approaches:

1. Jenkins-managed GitOps
2. Argo CD Image Updater (recommended)

>[!Note]
The CI and CD pipelines are intentionally **decoupled**. CI is responsible for **producing deployable artifacts**, while CD is responsible for **deploying the desired application** state to Kubernetes using **GitOps principles.**

---

# 1. CI (Continuous Integration) — SOP

## Objective

Transform source code into a **validated, secure, deployable artifact (Docker image)**.

---

## CI Trigger

1. Developer pushes source code to the Application Repository.
2. A Git webhook notifies the Jenkins Master.
3. The Jenkins Master dispatches the build to an available Jenkins Agent.

---

## CI Pipeline Flow

### Step 1. Source Code Checkout

* The Jenkins Agent checks out the latest source code from the Application Repository.
* Branch-based logic may apply (dev, main, etc.)

#

### Step 2. Build Stage

Executed on **Build Server (Agent)**. The build stage produces the application artifacts required to create the container image.

**Compile application**

  * Example:
      * Java → Maven/Gradle
      * Node.js → npm build
  * Resolve dependencies
  * Build ensures the code is structurally sound.

**Output:**

  * Compiled binaries / build artifacts

#

### Step 3. Unit Testing

Executed on **Build Server (Agent)**

  * Run automated tests
  * Validate code functionality
  * Unit tests ensure it's logically sound.

Decision:

  * Fail → Pipeline stops
  * Pass → Continue

#

### Step 4. Code Quality Analysis

**SonarQube checks**

  * Bugs
  * Code smells
  * Duplicated code
  * Security hotspots
  * Coverage
  * Maintainability

**Quality Gate:**

  * Fail → Pipeline stops
  * Pass → Continue

> The pipeline proceeds only if the configured SonarQube Quality Gate is passed.

#

### Step 5. Build Docker Image

**The Jenkins Agent builds a versioned Docker image using the application's Dockerfile.**

* Example:

	```
	docker build -t myapp:v1.0.3 .
	```


**Versioned Docker image**

* Output:

  ```
  myapp:v1.0.3
  ```

#

### Step 6. Security Scan (Image Level)

Using **Trivy**

* Scan Docker image for:

  * OS vulnerabilities
  * Package vulnerabilities
  * CVEs
  * Severity

**Decision:**

* Critical or High vulnerabilities (depending on organizational policy) may fail the pipeline.
* Clean → Continue

**Example:**

```
Critical = 0
High = 0
Medium = 5
```

#

### Step 7. Push to Container Registry

* Only after a successful scan push image to **Docker Hub** OR **Private Registry**
  
	```
	docker push myapp:v1.0.3
	```

* Output:\
	Stored, versioned image

#

### Step 8. Update GitOps Repository (Jenkins-managed GitOps only)

◾ In the **Jenkins-managed GitOps** approach, Jenkins updates the Kubernetes **deployment manifest** with the new image tag and **pushes** the changes to the **Manifest Repository**.

* Jenkins updates deployment manifest:

  * Changes image tag


◾ If **Argo CD Image Updater** is used, this step is skipped because **Argo CD Image Updater** automatically updates the **image tag** after detecting a new container image in the registry.


- Example:

	```yaml
	image: myapp:v1.0.3
	```

> This is the **handover point to CD**

---

## CI Final Output

- Verified code
- Tested application
- Secure Docker image
- Updated deployment manifest (Jenkins-managed GitOps only)

---

## CI Summary Flow

```text
Git Push
    ↓
Jenkins Master
    ↓
Jenkins Agent
    ↓

    ↓

		↓

    ↓

```

# 2. CD (Continuous Deployment) — SOP

## Objective

- Automatically deploy validated application to Kubernetes using GitOps.

---

## CD Trigger


- The CD pipeline starts when a change is committed to the Manifest Repository.

- The change may be generated by:

		- Jenkins (Jenkins-managed GitOps)
		- Argo CD Image Updater (recommended GitOps approach)

- Argo CD detects the repository change and starts synchronization.


---

## CD Pipeline Flow

### Step 1. Git Change

- A new commit is made to the Manifest Repository with the updated container image tag.
- The commit is generated by either:
  - Jenkins (Jenkins-managed GitOps)
  - Argo CD Image Updater
- Argo CD detects the repository change and starts the synchronization process.

### Step 2. Argo CD Detects Change

* Argo CD continuously monitors the Manifest Repository for changes.
* Detects new commit (image update)

#

### Step 3. Compare Desired vs Actual State

* Desired state → Git repo (YAML/Helm)
* Actual state → Kubernetes cluster

#

### Step 4. Apply Changes

- Argo CD applies the updated Kubernetes manifests to the Kubernetes cluster.

- Once the Deployment is updated:

    - Kubernetes detects the new image reference.
    - The kubelet on each worker node pulls the required container image from the registry.
    - Kubernetes performs a rolling update according to the Deployment strategy.

#

### Step 5. Kubernetes Handles Deployment

**Inside cluster:**

  * Pulls the container image from the registry
  * Create new pods
  * Gradually replace old pods

**Ensures:**

  * Zero downtime (if configured)

#

### Step 6. Health Check & Sync Status

**Argo CD verifies:**

  * Pods running
  * Services healthy

**Status:**

* Synced & Healthy → Success
* Degraded → Needs attention

---

### Step 7. Promotion Strategy (Multi-Cluster)

**Example deployment strategy:**

1. **Dev**\
		Auto deploy

2. **Staging**\
		Manual approval or automatic promotion based on organizational policy.

3. **Production**\
		Strict control (manual trigger recommended)

---

## CD Final Output

- Application deployed
- Running in Kubernetes
- Deployment state version-controlled in the Manifest Repository

---

## CD Summary Flow

```text
GitOps Repo Change → Argo CD Detect → Sync → Kubernetes Deploy → Pods Running
```

## Responsibility Separation

| Stage              | Tool                               | Responsibility                                          |
| ------------------ | ---------------------------------- | ------------------------------------------------------- |
| Source Control     | Git (Application Repository & Manifest Repository) | Stores application source code and Kubernetes manifests |
| CI Orchestration   | Jenkins                            | Build, test, scan, publish images                       |
| Code Quality       | SonarQube                          | Static code analysis                                    |
| Security           | Trivy                              | Container image vulnerability scanning                  |
| Container Registry | Docker Hub                         | Stores versioned container images                       |
| GitOps Automation  | Argo CD Image Updater *(optional)* | Updates image tags in Kubernetes manifests              |
| CD                 | Argo CD                            | Synchronizes Kubernetes with Git                        |
| Runtime            | Kubernetes                         | Runs containerized workloads                            |


---

## Key Concepts

1. CI produces a validated container image.
2. CD begins when the Manifest Repository changes.
3. Git is the single source of truth (GitOps).
4. Jenkins performs Continuous Integration.
5. Argo CD performs Continuous Deployment.
6. Argo CD Image Updater (optional) automates image tag updates in the Manifest Repository.
7. Kubernetes runs the deployed application workloads.
